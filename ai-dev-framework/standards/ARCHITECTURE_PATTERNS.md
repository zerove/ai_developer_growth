# 架构模式指南 (Architecture Patterns Guide)

> 常用架构模式和设计原则。

---

## 1. 架构原则

### 1.1 SOLID 原则

```yaml
solid:
  S - 单一职责: 一个类只有一个变化的原因
  O - 开闭原则: 对扩展开放，对修改关闭
  L - 里氏替换: 子类可以替换父类
  I - 接口隔离:  依赖倒置: 高层不依赖低层，都依赖抽象
```

### 1.2 DRY / KISS / YAGNI

```yaml
principles:
  DRY: 不要重复自己
  KISS: 保持简单
  YAGNI: 不要过度设计
```

### 1.3 关注点分离

```
将不同关注点分离到不同模块:
- 业务逻辑 vs 基础设施
- 表示层 vs 业务层 vs 数据层
- 配置 vs 代码
```

## 2. 分层架构

### 2.1

```
┌
│   表示层 (UI)    │  用户界面、API 端点
├─────────────────┤
│  业务层 (BLL)    │  业务逻辑、用例
├─────────────────┤
│  数据层 (DAL)    │  数据库、外部服务
└─────────────────┘
```

### 2.2 依赖规则

```
依赖方向: 表示层 → 业务层 → 数据层
禁止: 反向依赖、跨层依赖
```

## 3. 六边形架构 (Hexagonal / Ports & Adapters)

### 3.1 核心概念

```
         ┌─────────────────────┐
         │      业务核心       │
         │  (领域模型+用例)    │
         └─────────┬───────────┘
                   │
    ┌──────────────┼──────────────┐
    │              │              │
┌───┴───┐    ┌────┴────┐    ┌───┴───┐
│ REST  │    │  数据库  │    │ 消息队列│
│ API   │    │  适配器  │    │  适配器 │
└───────┘    └─────────┘    └───────┘
   入站端口      出站端口       出站端口
```

### 3.2 核心规则

```yaml
hexagonal_rules:
  - 业务核心不依赖外部
  - 外部通过端口与核心交互
  - 适配器实现端口接口
  - 可以替换任何外部依赖
```

## 4. 事件驱动架构

### 4.1 事件模式

```yaml
event_patterns:
  事件通知: "发生了什么"
  事件溯源: "所有状态变化都是事件"
  CQRS: 命令和查询分离
```

### 4.2 事件结构

```yaml
event_structure:
  - id: 唯一标识
  - type: 事件类型
  - timestamp: 发生时间
  - aggregate_id: 聚合 ID
  - payload: 事件数据
  - metadata: 元数据
```

## 5. 微服务架构

### 5.1 服务边界

```yaml
service_design:
  - 按业务能力划分
  - 每个服务独立数据库
  - 服务间通过 API 通信
  - 使用 API Gateway
```

### 5.2 通信模式

```yaml
communication:
  同步: REST, gRPC
  异步: 消息队列, 事件
  服务发现: DNS, Consul
```

## 6. 领域驱动设计 (DDD)

### 6.1 核心概念

```yaml
ddd_concepts:
  - 领域: 业务问题空间
  - 限界上下文: 领域边界
  - 聚合: 一组相关对象
  - 实体: 有唯一标识的对象
  - 值对象: 无唯一标识的对象
  - 领域事件: 领域中发生的事情
```

### 6.2 战略设计

```
1. 识别限界上下文
2. 定义上下文映射
3. 建立通用语言
4. 划分团队边界
```

### 6.3 战术设计

```
实体 + 值对象 → 聚合根 → 领域服务 → 领域事件
```

## 7. 设计模式

### 7.1 创建型模式

```yaml
creational_patterns:
  Factory: 创建对象而不指定具体类
  Builder: 分步构建复杂对象
  Singleton: 确保一个类只有一个实例
  Prototype: 通过复制创建对象
```

### 7.2 结构型模式

```yaml
structural_patterns:
  Adapter: 将不兼容的的接口
  Decorator: 动态添加职责
  Facade: 提供简化的接口
  Proxy: 提供占位符以控制访问
```

### 7.3 行为型模式

```yaml
behavioral_patterns:
  Strategy: 定义算法族，使它们可以互换
  Observer: 定义一对多的依赖关系
  Command: 将请求封装为对象
  State: 允许对象在状态改变时改变行为
```

## 8. 错误处理架构

### 8.1 错误边界

```yaml
error_boundaries:
  - 在每个层边界处理错误
  - 使用 Result/Either 类型
  - 错误可以被匹配和转换
  - 不要让错误跨越边界
```

### 8.2 错误恢复

```
1. 重试: 临时性故障
2. 降级: 非关键功能
3. 熔断: 防止级联故障
4. 回退: 使用默认值
```

## 9. 缓存架构

### 9.1 缓存层次

```yaml
cache_levels:
  L1: 进程内缓存
  L2: 分布式缓存
  L3: 数据库缓存
```

### 9.2 缓存策略

```yaml
caching_strategies:
  - Cache-Aside: 应用管理缓存
  - Write-Through: 同时写入缓存和数据库
  - Write-Behind: 异步写入数据库
  - Read-Through: 缓存管理数据加载
```

```yaml
observability:
```

### 10.2 分布式追踪

```yaml
  - 传播 Context
```
