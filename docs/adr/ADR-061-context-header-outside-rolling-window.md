# ADR-061: CONTEXT.md 固定头部必须独立于滚动窗口，且校验不得 fail-open

## 状态
接受

## 日期
2026-10-02

## 背景

`CONTEXT.md` 曾在 2026-08-23 丢失全部固定头部，退化为**纯同步日志**（1142 行、
50 条 `## 更新记录:`、首行即记录标题）。项目定位、状态表、关键约束等人工维护的
上下文全部消失，只剩重复的"Git 变更同步 / 变更文件 N 个"。

追溯提交 `2777766`（2026-08-23）定位到根因，涉及**两个叠加缺陷**：

### 缺陷 1：组装顺序反了

`synthesize_context_update` 把新记录拼在已有内容**之前**：

```python
update = f"""
## 更新记录: {timestamp}
...
{current_context}      # <- 头部落在这里
"""
```

记录边界只由**下一个** `## 更新记录:` 决定。于是"新记录 + 头部 + 历史记录"被
`_prune_update_entries` 整体识别为**一条**记录（标题取自新记录，正文却包含头部），
头部因此落入滚动窗口参与裁剪。窗口为 50，即第 51 次同步时头部被静默丢弃。

复现（`max_update_entries=5`，连续 40 次同步）：第 6 次起头部消失。

### 缺陷 2：`validate_context` 是 fail-open

```python
for name, passed in checks:
    print_check(f"CONTEXT.md - {name}", passed)  # 只打印
...
print_check("验证通过", True)  # 无条件打印
return 0  # 恒为 0
```

即使全部子检查失败，函数仍打印"验证通过"并返回 0。`.jcode/hooks.json` 中
`weekly-context-sync`（`action: validate`，每周一 11:00）据此判定通过。

且其检查是**全文 substring**（`"项目状态" in content`），被窗口吞掉的恰好就是
含这些词的段落 —— 即便修好退出码，位置性信息丢失也无法被发现。

## 决策

**1. 显式分离固定头部与记录区，头部恒为文档第一段。**

- 新增 `_split_header_and_entries()`：以首个 `## 更新记录:` 为界切分
- 新增 `_render()`：按 `[固定头部, 记录区]` 组装，保证头部排在所有记录之前
- 组装顺序改为 `header → 新记录 → 历史记录`
- 抽出 `_ENTRY_PREFIX` 常量，消除头部识别与裁剪两处字面量漂移

**2. `validate_context` 改为结构校验 + 真实退出码。**

- 关键词检查作用于**头部区**而非全文，关键词出现在记录区不算数
- 新增"固定头部非空""以一级标题开头"两项结构检查
- 任一子检查失败即返回 1，并列出未通过项；移除无条件"验证通过"

**3. 补齐回归测试**，锁定三条契约：头部在所有记录之前、多次同步后头部不丢、
头部不被吸收进记录正文。

## 后果

### 正面

- `CONTEXT.md` 固定头部恢复并锁定，不再可能被同步流程静默摧毁
- `weekly-context-sync` 从"恒通过"变为真实门禁，退化形态会被检出
- 头部识别与窗口裁剪共用同一常量，消除两处逻辑漂移的隐患

### 负面 / 取舍

- `validate_context` 从 fail-open 转为 fail-closed，历史上退化的 `CONTEXT.md`
  会立即被该校验判失败（本仓已在同批次修复）；其他使用此 skill 的仓库首次
  运行 `validate` 可能转为非 0，属预期行为
- 头部区内容需人工维护，不再由同步流程自动生成

### 验证

- 变异测试：注入缺陷 1（把组装顺序改回 `entry, header, entries`）后，新增的 4 个
  头部测试全部失败；恢复后全绿 —— 确认测试真能捕获该缺陷而非装饰性断言
- 端到端：真实 `CONTEXT.md` 经 `synthesize_context_update` 往返后，头部完整、
  记录区正确裁剪至 50 条
- `pytest tests/test_context_sync_prune.py tests/test_jcode_context_sync.py`：67 passed
  （新增 14 个用例）
- `validate` 对退化态返回 1，对恢复态返回 0
- 边界场景：空文档、仅头部无换行、仅记录无头部、头部后紧跟记录无空行、CRLF 行尾
  —— 头部均正确保留

### 已知局限

记录边界采用**行首前缀匹配**（`startswith("## 更新记录:")`）。若头部中出现围栏代码块
（``` ```），且块内某行恰以 `## 更新记录:` 开头，该行会被误判为记录起点，头部随之
在渲染时被截断。

本次不修，理由：真实头部不含此类内容，修复需引入 Markdown 围栏状态机，复杂度与
收益不匹配。**规避方式**：头部内不要在围栏代码块中书写以 `## 更新记录:` 开头的行。
已记入 ROADMAP v2.26.0 候选，若将来确有需要再引入围栏感知切分。
