# Agent 开发流程规范

本文档定义了 AI Agent 的开发全流程标准，确保从需求到交付的质量和一致性。

> **通用版本**: 本文档的通用版本见 `GOVERNANCE.md`（项目根目录）。本文档包含本项目的特定工具和流程。

---

## 核心理念：意图引导 + 质量门禁

Agent 开发不是一次性的代码生成，而是**"定义 → 实现 → 验证 → 沉淀"**的闭环迭代。

---

## 全生命周期流程

```
需求分析 → Prompt 设计 → 实现编码 → 自动化审计 → 资产更新
   ①          ②          ③          ④           ⑤
```

### ① 需求分析

**目标**: 明确 agent 的职责、边界和验收标准。

**输入**:
- 业务需求描述
- 现有代码库结构
- 已有 agent 定义（避免职责重叠）

**输出**:
- Agent 职责描述（一句话）
- 工具需求列表
- 验收标准

**检查清单**:
- [ ] 职责边界清晰，与现有 agent 无重叠
- [ ] 工具需求明确（最小权限原则）
- [ ] 验收标准可量化、可测试

### ② Prompt 设计

**目标**: 编写符合 `prompt-standards.md` 的 agent 定义。

**步骤**:
1. 参照 `agent-prompt-template.md` 填写结构
2. 指令逐条编写，确保具体、可验证
3. 工具列表按最小权限分配
4. 自查 `prompt-standards.md` 中的反模式

**质量门禁**:
- [ ] 指令具体，无模糊表述
- [ ] 每条指令可通过 LSP/测试/grep 验证
- [ ] 工具列表无冗余
- [ ] 无职责重叠的 agent

### ③ 实现编码

**目标**: 将 agent 定义集成到项目中。

**编码规范**:

| 维度 | 标准 |
|------|------|
| 错误处理 | 使用 `thiserror` 定义 Error，禁止 `unwrap()`/`expect()` |
| 异步 | 使用 `tokio` + `async-trait` |
| 类型安全 | 禁止 `as any` / `@ts-ignore` / `@ts-expect-error` |
| 文件大小 | 单文件不超过 300 行 |
| 函数大小 | 单函数不超过 50 行 |

**提交规范**:
```bash
# 好的提交
git commit -m "feat(agent): add core-engineer agent definition"

# 避免的提交
git commit -m "feat: add agents"  # 太大，难以追踪
```

### ④ 自动化审计

**目标**: 使用 AI-Context-Sync 工具验证实现质量。

**审计流程**:

```bash
# 1. 同步项目上下文
ai_sync

# 2. 架构合规审计
ai_guard  # 检查是否符合架构决策

# 3. 开发规范审计
ai_audit  # 检查代码是否符合规范

# 4. 完整流水线（可选）
ai_flow   # 执行完整开发流水线
```

**质量门禁**:
- [ ] `ai_guard` 通过（架构合规）
- [ ] `ai_audit` 通过（规范合规）
- [ ] LSP 无错误
- [ ] 测试通过

### ⑤ 资产更新

**目标**: 更新项目文档和知识库。

**更新内容**:

| 资产 | 更新时机 | 负责人 |
|------|----------|--------|
| `CONTEXT.md` | 每次重大迭代后 | Agent |
| `ADR.md` | 关键架构决策时 | Agent |
| `AGENTS.md` | 新增/修改 agent 时 | Agent |
| `UBIQUITOUS_LANGUAGE.md` | 新增领域术语时 | Agent |

**更新命令**:
```bash
# 更新项目上下文
ai_sync

# 跟踪决策历史
ai_trace

# 生成架构图
ai_map
```

## 并行执行策略

### 可并行的任务

| 任务组 | 包含任务 | 依赖 |
|--------|----------|------|
| **探索组** | explore agents | 无 |
| **实现组** | 各 agent 编码 | 探索组完成 |
| **审计组** | ai_audit, ai_guard | 实现组完成 |
| **文档组** | CONTEXT.md, ADR.md | 审计组完成 |

### 串行的任务

```
需求分析 → Prompt 设计 → (实现编码 | 探索) → 自动化审计 → 资产更新
```

**关键路径**: 需求 → Prompt → 实现 → 审计 → 更新

## 质量标准

### Agent 定义质量

| 指标 | 目标 | 验证方式 |
|------|------|----------|
| 指令具体性 | 100% 可验证 | 逐条检查 |
| 工具最小化 | 无冗余工具 | 与职责匹配 |
| 职责唯一性 | 无重叠 | 与现有 agent 对比 |
| 文档完整性 | 所有字段填写 | 模板检查 |

### 代码质量

| 指标 | 目标 | 验证方式 |
|------|------|----------|
| 错误处理 | 无 `unwrap()` | grep 检查 |
| 类型安全 | 无类型逃逸 | LSP 诊断 |
| 测试覆盖 | > 80% | 覆盖率报告 |
| 文件大小 | < 300 行 | wc -l |

## 反模式

### ❌ 禁止的流程

1. **跳过需求分析**: 直接编写 agent 定义
2. **跳过审计**: 编码后直接提交
3. **批量提交**: 多个不相关的变更合为一个 commit
4. **忽略文档**: 实现后不更新 CONTEXT.md

### ✅ 推荐的流程

1. **需求先行**: 明确职责再动手
2. **审计必做**: 每次实现后运行 ai_audit + ai_guard
3. **原子提交**: 一个功能点一个 commit
4. **文档同步**: 实现后立即更新文档
