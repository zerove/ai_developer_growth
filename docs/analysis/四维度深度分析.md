## 一、设计维度 (Design)

### 1.1 设计理念与架构目标

**核心理念**: "AI 能写 80% 代码时，你的价值在定义问题、系统设计、快速迭代。"这不是一个"写代码的项目"，而是一个"治理知识体系"——需要一套跨项目通用的质量门禁框架。

**已知优秀实践**:
- [x] 五层分层架构（External → Interface → Application → Domain → Infrastructure → Framework → Config），严格依赖方向向内收束
- [x] ADR（Architecture Decision Record）驱动，70 条决策文档沉淀为组织记忆
- [x] 自反性治理：门禁自己检查自己运行时的状态（ci-heartbeat / ci-alert 机制）
- [x] 语义检查降级可见性：tree-sitter 缺失时产出 `semantic-degraded` error Issue，杜绝"假绿灯"
- [x] 事件驱动 Hook 系统：`.jcode/hooks.json` 定义 `on_commit/on_pr/on_merge/scheduled` 四类事件

### 1.2 可优化设计问题

| # | 问题 | 严重度 | 建议 |
|---|------|--------|------|
| D-01 | **语义规则插件系统碎片化**: `semantic_rules.py` 与 `ast_semantic.py` 存在重复实现——`checker.py` 内有 `check_python_bare_raise` 直接调用 AST walker，而 `semantic_rules.py` 是独立插件入口。两者职责边界模糊，新增语义规则需双入口注册。 | 中 | 将 `ast_semantic` 统一收敛到 `plugins` 子系统中，取消 `check_python_bare_raise` 直接路径，保证单入口 |
| D-02 | **文档与代码的"隐性耦合"**: MOC（391 篇文档）反向索引代码 10 个示例项目，但 `link_auditor` 只校验链接可达性，不校验"文档是否还反映代码变更"。当示例代码重构后，历史链接引用可能指向过时实现 | 中高 | 增加 `doc_version_sync` 检查：扫描示例目录变更时，校验相关 `case-studies` 描述与新代码的一致性 |
| D-03 | **`issue.column` 语义漂移风险**: `models.py` 中的 `Issue` 模型 `column` 字段为 0 默认值，`adg_cli/core.py` 的 `Issue` 子类重排了位置参数但注释说"避免静默错位"。虽有防护，但两套模型间的 column 语义不一致仍是隐患 | 低 | 明确 `column` 在两套 Issue 中作为"列偏移量"还是"字符起始位置"，或在两处均采用统一的 `(line, column)` 序 |
| D-04 | **单点依赖收敛**: `Checker` 主流程 (`checker.py`) 直接 import 了 `anti_pattern_checker`, `complexity_checker`, `naming_checker`, `models`, `context`, `plugins`, `rule_loader`, `arch.*` 等模块。随着规则引擎扩张，依赖图复杂度线性增长 | 中 | 将核心 checker 收敛到依赖注入容器，子 checker 通过依赖接口传递，降低耦合度 |
| D-05 | **缓存签名粒度不足**: `_check_with_cache` 签名包含 `rules_hash:s{semantic}:l{run_linters}` 但未包含 per-file 的 AST 缓存的额外标识。当某文件代码改写后 parser tree-sitter 缓存可能失效但被误复用（`use_cache=True` 默认关闭的场景） | 低 | 文件级 mtime+size 已足够，当前是唯一标识；但语义模式应 加入签名校验 |

## 二、架构维度 (Architecture)

### 2.1 整体架构概览

```
┌──────────────────────────────────────────────────────────────┐
│                      Hook 事件系统 (.jcode/hooks.json)        │
│           on_commit → 质控审计 │ on_pr → 全量审计             │
│            on_merge → 上下文同步 │ scheduled → 周频任务         │
└───────────────────────────┬────────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │  核心引擎    │  │  规则引擎    │  │  自动化脚本   │
  │ adg_cli     │  │  rules_engine│  │ tools/scripts│
  │  parser.py   │  │  AST+正则    │  │  (~270文件)  │
  │  core.py    │  │  +语义插件   │  │  hooks/Rules │
  └──────┬──────┘  └──────┬──────┘  └─────────────┘
         │                │
         ▼                ▼
  ┌────────────────────────────────────────┐
  │           AutoFixOrchestrator           │
  │  Regex + Ruff + Isort + Autoflake      │
  └────────────────────────────────────────┘
         │
         ▼
  ┌────────────────────────────────────────┐
  │      examples/ × 10 项目               │
  │      + docs/ (391篇) + case-studies/   │
  └────────────────────────────────────────┘
```

### 2.2 关键架构决策与可优化点

| # | 架构问题 | 说明 | 改进方向 |
|---|----------|------|----------|
| A-01 | **CLI 双入口冗余**: `adg_cli/` 与 `hooks_runner.py` 共存。前者面向终端用户，后者面向 Git hook 自动触发。两套 parser 构建逻辑重叠（都在 `parser.py` 里），且共享 FIX_RULES 常量。可抽公共 parser 工厂 | 抽取 `_shared_parsers.py` 作为公共 argparse builder，两个入口各自复用 | 中 |
| A-02 | **Worker 进程隔离缺陷**: `ProcessPoolExecutor` 中每个 worker 持独立 SQLite 连接，通过 `initializer=_worker_init` 传参。但在非 fork 启动方式下（Windows），worker 拿不到表自动回退逐文件 spawn，增加了启动开销 | Windows 兼容层应内嵌独立的快速路径（`threading` + SQLite WAL），无需回退到 ProcessPool | 低 |
| A-03 | **依赖图分析泛化**: `DependencyGraph.analyze_directory()` 仅对 Python 做依赖分析（`analyze_directory` 可能假设 Python 项目）。工具依赖检测 (`tools/scripts/dependency_graph.py`) 却是通用 | `DependencyGraph` 应支持 multi-language parser 注册（YAML/JSON config 同时解析），消除两层实现 | 高 |
| A-04 | **语义规则热加载缺失**: 新增 `SemanticRule` 不修改 `checker.py` 已能运行，但 `store.py` 的规则签名计算依赖全量加载所有规则。当规则持续增长时需重启 | 实现内存中的规则注册表 + mtime 触发的热更新，无需重启引擎 | 中 |
| A-05 | **示例项目与主仓库边界模糊**: 10 个示例项目（ai-context-sync、multi-agent-orch 等）有自己的 pyproject.toml 和 CI，但它们又受主项目的 `adg check` 门禁约束。缺少清晰的"例外部隔离"策略 | 为每个示例添加 `examples/<name>.jcode/scope: demo` marker，让 skip_patterns / context markers 自动排除 | 中 |

### 2.3 架构稳健性评估

**已解决的关键架构脆弱点**:
- ADR-064 语义降级假绿灯 → ✅ 已修复（`semantic-degraded` error Issue 可见）
- ADR-074/076/078 skipped 文件静默 → ✅ 已修复（Phase 33b-13）
- ADR-079 路径引导 `python -m` vs `python path.py` → ✅ 已修复（`_bootstrap` 重构）
- GitHub Actions 月配额耗尽 → ✅ 已通过 `ci-heartbeat` 本地执行绕过 CI 配额

### 3.2 关键实现可优化点

| # | 问题 | 位置 | 问题描述 | 改进建议 |
|---|------|------|----------|----------|
| I-01 | **FIX_RULES 行内正则注入风险**: `RegexFixProvider.generate_fixes` 对 `issue.line` 执行 `re.sub` 前不验证 `rule_id` 是否与正则 pattern 一致，可能出现替换替换了错误位置的行内容 | `auto_fix.py:546` | 三方不可信输入（original_line / rule_id / replacement）构成注入面。建议改为仅用 `re.subn` 替换整个文件 content 而非逐行替换 |
| I-02 | **`GuardPattern` 反模式逻辑薄弱**: `regex_cache.guard_pattern` 对 `auto_fix/rule_id` 走字符串匹配而非正则匹配，意味着如果恶意构造 rule_id 可绕过 guard。虽然实践中不会触发，但无防护 | `regex_cache.py` | 升级 guard 为基于 `to_dict() → re.compile(pattern)` 的等价检查，匹配 fix_replacement 字段而非 rule_id |
| I-03 | **FIX_ACTIONS `confidence` 全为硬编码**: `confidence: 0.8/0.9/0.95` 从没动态计算。工具 provider（ruff）confidence 高但 regex 低，交互模式应根据 provider 能力调优 | `auto_fix.py:558-582` | 根据 provider 名称和能力分级设置 confidence 区间 |
| I-04 | **Worker 初始化顺序潜在 Bug**: `ProcessPoolExecutor` 使用 `chunksize=16`，但 `_worker_init` 先做 warmup 再初始化。`warmup_rules` 通过 fork 继承，如果后续全局变量被污染可能影响 worker | `checker.py:483-484` | 添加 `worker_init` 的稳定性断言：每个 worker 确认 `compute_rules_signature` 正常返回 |
| I-05 | **多语言 lint 规则 ID 前缀分散**: 项目最新 commit（cb58bc9）统一了前缀但部分旧规则 ID 未对齐。例如 `go-err-nil` vs `common-try-except` 等 | `custom_rules.yml` | 启用 `--strict` CI 模式校验所有规则 ID 一致性 |
| I-06 | **示例项目测试覆盖率偏低**: `examples/ai-navigation-web` 和 `capability-radar` 没有明确的测试阈值，部分只有样例 JSON 测试 | 各示例 pyproject.toml | 为每个示例设置 `cov_min: 50%` 的 CI 门禁 |
| I-07 | **`lint_runner` 缺失文件**: `tools/scripts/lint_runner.py` 不存在，实际 lint 走的是 `rules_engine._checker_linters` 或外部工具链。长期依赖未显式文档化 | tools/scripts/ | 在 README / `.adg` 规范中明确定义 lint 引擎的映射表 |

## 四、性能维度 (Performance)

### 4.1 性能基准数据

从提交历史可见关键优化成果:

| 优化项 | Before | After | 来源 |
|--------|--------|-------|------|
| 项目文件遍历 | 22755 路径, 0.82s | 就地剪枝排除目录后显著改善 | ADR-014 |
| 规则测试 B+N 驱动 | N+1 风险误报 25 个 | profile 验证全部为误报 → info | severity_overrides.yml |

### 4.2 性能瓶颈与优化方向

| # | 瓶颈 | 影响 | 优化建议 | 预估收益 |
|---|------|------|----------|----------|
| P-01 | **全仓默认串行检查**: `jobs=1` 是 argparse 默认值，557 文件串行跑规则引擎会很慢 | 每次 `adg check .` > 5s | 对于规则引擎纯 CPU 任务，检测到 `len(files) > 4 && jobs == 1` 时自动提升 workers 到 min(cpu_count, 4) | 2-3x 速度提升；**2026-11-09 已实施**：`cmd_check._resolve_jobs`（显式 `--jobs` > `[tool.adg].jobs` > 4），JSON `meta.jobs` 与实际执行一致 |
| P-02 | **LSP Server 单文件处理**: 8080 端口阻塞，每个新连接触发全流程重算 | IDE 集成延迟 | 实现文件级增量缓存（已做但未启用），新连接复用上次 parse 结果 | IDE 侧体感 3-5x |
| P-03 | **MkDocs 文档构建无增量**: 每次 `mkdocs build` 391 篇全量扫描 | 构建时间 > 30s | 基于 mtime 增量：仅扫描 changed files，复用已构建 HTML 片段 | 10-20s |
| P-04 | **autoflake 未使用导入检测`: 每文件一次 subprocess spawn | 557 文件一次约 5-10s | 批量合并调用：autoflake --in-place --exclude <pathes> 一次处理 | ~3s |
| P-05 | **dependency_graph 多语言解析**: `analyze_directory` 仅解 Python | 多语言项目耗时翻倍 | 实现 JSON/YAML 配置同时解析，复用 parser 注册机制 | 50% 耗时缩减 |

### 4.3 安全与 ReDoS 防护

**已建立的反模式防护**:
- [x] 正则 pattern 预编译（`regex_cache.py`)
- [x] ReDoS 门禁：`pyproject.toml` 中的规则模式通过有限字符集校验
- [x] Guard 模式拦截第三方代码 pattern 注入

**待加固区域**:
- [ ] `user-provided custom_rules.yml` 的 pattern 字段未做 ReDoS 校验——恶意 pattern 可拖垮全仓检查
- [ ] `FixPlan.group_by_rule()` 批量 PR 生成的 `diff` 内容未做 HTML 转义（防止 diff 注入到 README 渲染）
- [ ] webhook notify (`slack://...` / `dingtalk://...`) 的 URL 缺少 SSRF 校验，远程服务可接管本地端口
