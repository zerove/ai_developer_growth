## 一、设计维度 (Design)

### 1.1 设计理念与架构目标

**核心理念**: "AI 能写 80% 代码时，你的价值在定义问题、系统设计、快速迭代。"这不是一个"写代码的项目"，而是一个"治理知识体系"——需要一套跨项目通用的质量门禁框架。

**已知优秀实践**:
- [x] 五层分层架构（External → Interface → Application → Domain → Infrastructure → Framework → Config），严格依赖方向向内收束
- [x] ADR（Architecture Decision Record）驱动，70 条决策文档沉淀为组织记忆
- [x] 自反性治理：门禁自己检查自己运行时的状态（ci-heartbeat / ci-alert 机制）
- [x] 语义检查降级可见性：tree-sitter 缺失时产出 `semantic-degraded` error Issue，杜绝"假绿灯"
- [x] 事件驱动 Hook 系统：`.jcode/hooks.json` 定义 `on_commit/on_pr/on_merge/scheduled` 四类事件

### 1.2 可优化设计问题

## 二、架构维度 (Architecture)

### 2.1 整体架构概览

```
┌──────────────────────────────────────────────────────────────┐
│                      Hook 事件系统 (.jcode/hooks.json)        │
│           on_commit → 质控审计 │ on_pr → 全量审计             │
│            on_merge → 上下文同步 │ scheduled → 周频任务         │
└───────────────────────────┬────────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
  │  核心引擎    │  │  规则引擎    │  │  自动化脚本   │
  │ adg_cli     │  │  rules_engine│  │ tools/scripts│
  │  parser.py   │  │  AST+正则    │  │  (~270文件)  │
  │  core.py    │  │  +语义插件   │  │  hooks/Rules │
  └──────┬──────┘  └──────┬──────┘  └─────────────┘
         │                │
         ▼                ▼
  ┌────────────────────────────────────────┐
  │           AutoFixOrchestrator           │
  │  Regex + Ruff + Isort + Autoflake      │
  └────────────────────────────────────────┘
         │
         ▼
  ┌────────────────────────────────────────┐
  │      examples/ × 10 项目               │
  │      + docs/ (391篇) + case-studies/   │
  └────────────────────────────────────────┘
```

### 2.2 关键架构决策与可优化点

| # | 架构问题 | 说明 | 改进方向 |
|---|----------|------|----------|
| A-01 | **CLI 双入口冗余**: `adg_cli/` 与 `hooks_runner.py` 共存。前者面向终端用户，后者面向 Git hook 自动触发。两套 parser 构建逻辑重叠（都在 `parser.py` 里），且共享 FIX_RULES 常量。可抽公共 parser 工厂 | **2026-11-12 已实施**：adg_cli parser 改为 `_COMMAND_BUILDERS` registry 统一装配 + `commands.get_command_handler` 单一解析入口；hooks_runner 侧另有独立 `_build_parser`（本次未合并） | 中 |
| A-02 | **Worker 进程隔离缺陷**: `ProcessPoolExecutor` 中每个 worker 持独立 SQLite 连接，通过 `initializer=_worker_init` 传参。但在非 fork 启动方式下（Windows），worker 拿不到表自动回退逐文件 spawn，增加了启动开销 | Windows 兼容层应内嵌独立的快速路径（`threading` + SQLite WAL），无需回退到 ProcessPool | 低 |
| A-03 | **依赖图分析泛化**（已修正）: `DependencyGraph` 早已支持 6 种语言（`LANGUAGE_EXTS` + `IMPORT_PATTERNS`），但 import 说明符**未解析**到真实文件（边指向不存在的节点）→ 循环依赖检测**永远不可能命中**（静默假绿灯），hub 统计还把标准库算进去。现改为：先建"模块路径→文件"索引再解析 import（Python 走 `ast`，其余走正则），只保留树内依赖；并让 `.adg/architecture.yml` 的 `cycle_detection`/`hub_detection` 段落真正生效 | `tools/scripts/rules_engine/arch/dependency_graph.py` | 契约由 `tests/test_dependency_graph_resolution.py` 锁定；检查恢复可用后**拆除了全部 4 组存量循环**（豁免清单已清空） |
| A-04 | **语义规则热加载缺失**: 新增 `SemanticRule` 不修改 `checker.py` 已能运行，但 `store.py` 的规则签名计算依赖全量加载所有规则。当规则持续增长时需重启 | 实现内存中的规则注册表 + mtime 触发的热更新，无需重启引擎 | 中 |
| A-05 | **示例项目与主仓库边界模糊**: 10 个示例项目（ai-context-sync、multi-agent-orch 等）有自己的 pyproject.toml 和 CI，但它们又受主项目的 `adg check` 门禁约束。缺少清晰的"例外部隔离"策略 | 为每个示例添加 `examples/<name>.jcode/scope: demo` marker，让 skip_patterns / context markers 自动排除 | 中 |

### 4.2 性能瓶颈与优化方向

| # | 瓶颈 | 影响 | 优化建议 | 预估收益 |
|---|------|------|----------|----------|
| P-01 | **全仓默认串行检查**: `jobs=1` 是 argparse 默认值，557 文件串行跑规则引擎会很慢 | 每次 `adg check .` > 5s | 对于规则引擎纯 CPU 任务，检测到 `len(files) > 4 && jobs == 1` 时自动提升 workers 到 min(cpu_count, 4) | 2-3x 速度提升；**2026-11-09 已实施**：`cmd_check._resolve_jobs`（显式 `--jobs` > `[tool.adg].jobs` > 4），JSON `meta.jobs` 与实际执行一致 |
| P-02 | **LSP Server 单文件处理**: 8080 端口阻塞，每个新连接触发全流程重算 | IDE 集成延迟 | **已实施（2026-11-12）**：诊断结果按文件内容 SHA-256 缓存（uri → (hash, diagnostics)），didChange/didSave/didClose 失效，命中复用 | IDE 侧体感 3-5x |

| P-04 | **autoflake 未使用导入检测`: 每文件一次 subprocess spawn | 557 文件一次约 5-10s | 批量合并调用：autoflake --in-place --exclude <pathes> 一次处理 | ~3s |
| P-05 | **dependency_graph 多语言解析**（已修正，2026-11-12）: 现 import 会解析到树内真实模块（Python 走 `ast` 精确取 import，其余语言走正则），循环依赖检测恢复可用；`.adg/architecture.yml` 的相关段落不再是摆设 | `tools/scripts/rules_engine/arch/dependency_graph.py` | 多语言项目不再只解析 Python；存量循环已逐条登记豁免并附原因 |

### 4.3 安全与 ReDoS 防护

**已建立的反模式防护**:
- [x] 正则 pattern 预编译（`regex_cache.py`)
- [x] ReDoS 门禁：`pyproject.toml` 中的规则模式通过有限字符集校验
- [x] Guard 模式拦截第三方代码 pattern 注入

**待加固区域**:
- [ ] `user-provided custom_rules.yml` 的 pattern 字段未做 ReDoS 校验——恶意 pattern 可拖垮全仓检查
- [ ] `FixPlan.group_by_rule()` 批量 PR 生成的 `diff` 内容未做 HTML 转义（防止 diff 注入到 README 渲染）
- [ ] webhook notify (`slack://...` / `dingtalk://...`) 的 URL 缺少 SSRF 校验，远程服务可接管本地端口
