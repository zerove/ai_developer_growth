# 我用 ADG 扫了 5 个顶级开源项目——发现了什么？

## 背景与挑战

作为 ADG（AI Developer Governance）的开发者，我需要回答一个关键问题：这个工具在**真实世界**中到底有没有用？

**核心挑战**：
1. **真实性验证**：单元测试只能验证规则引擎的正确性，无法证明工具能发现真实项目中的问题
2. **误报控制**：对知名开源项目扫描，需要区分真实问题与误报（目标：误报率可接受）
3. **规模压力**：覆盖 4250+ 文件、3 种 Python 框架 + 1 工具库 + 1 个 Rust 项目，规则引擎需跨语言一致工作

为此选择 5 个顶级开源项目（FastAPI/Flask/Django/httpx/ruff）进行实战扫描验证。

---

## AI 协作过程

### Phase 1: 需求分析 & PRD
- **人**: 制定扫描方案与项目选择标准、定义成功指标（误报率、发现真实问题数）
- **AI**: 协助分析项目规模、星标数、技术栈分布，生成对比表格
- **验证方式**: 人工确认项目选择合理性
- **耗时对比**: 传统 2 小时 → AI 协作 30 分钟

### Phase 2: 架构设计 & 契约定义
- **人**: 定义扫描流程：全量扫描 → 规则分级 → 人工审计 → 真实问题确认 → 规则改进
- **AI**: 生成扫描脚本、输出格式规范、误报分类模板
- **验证方式**: 试运行 1 个小项目验证流程
- **耗时对比**: 传统 4 小时 → AI 协作 1 小时

### Phase 3: 迭代编码 (TDD 循环)
- **循环次数**: 5 次（对应 5 个项目）
- **典型循环**: `adg scan` 扫描 → 解析输出 → 人工审计 → 规则改进 → 重新扫描验证
- **关键 Bug/挑战**: 测试文件大量误报、Rust 规则不足、TYPE_CHECKING 块误报
- **修复方式**: 新增 exclude_patterns、白名单机制、TYPE_CHECKING 排除、去重逻辑

### Phase 4: 优化 & 交付
- **人**: 撰写案例报告、整理规则效率排名、制定 P0-P3 修复清单
- **AI**: 生成效率对比表格、整理误报分析、生成引擎改进清单
- **最终验收**: 所有 5 个项目扫描可复现，5 项引擎改进已落地 4 项

## 关键洞察

### 1. ADG 能发现真实问题
5 个项目中都找到了有实际价值的问题，尤其在安全方面（硬编码密钥 18 个、eval 7 个、文件泄漏 6 个）。Django 2500+ 文件发现 25 个真实问题，问题密度是 FastAPI 的 2.5 倍。

### 2. 规模越大工具价值越显著
Django 2500+ 文件的问题密度是 FastAPI 500+ 文件的 2.5 倍——工具的作用在大型项目中更显著。传统人工审计无法在合理成本内覆盖 4250 个文件。

### 3. 质量好的项目不意味着零问题
FastAPI 是公认的高质量项目（测试覆盖率 96%），仍有 2 个可修复的安全问题（测试配置中的硬编码密钥）。高质量测试套件 = 更低的安全风险，但不等于零风险。

### 4. 规则引擎需要持续迭代
15% 的误报率虽然可接受，但通过 exclude_patterns 和注释豁免可以进一步降低。本次扫描直接驱动了 5 项引擎改进（exclude_patterns、白名单、TYPE_CHECKING 排除、去重、Rust 规则）。

### 5. 跨语言扫描是差异化优势
同时扫描 Python 和 Rust 项目，统一规则框架，是 ADG 相比单一语言 linter 的核心价值。Rust 的类型系统天然排除了许多 Python 问题，但 unsafe 块需要专门规则。

## 适用场景

- [x] **最适用**: 对大型/中型开源或存量项目做安全与质量基线扫描
- [x] **最适用**: 跨语言（Python/Rust/Go/TS）统一治理规范的团队
- [x] **最适用**: 规则引擎开发者的误报分析与规则迭代（本案例直接驱动 5 项引擎改进）
- [x] **最适用**: CI 集成前的代码质量快速摸底
- [ ] **不适用**: 需要语义级理解（如业务逻辑正确性）的场景（ADG 定位为模式级治理工具）
- [ ] **团队要求**: 熟悉命令行工具、能解读规则文档、有代码审计基础
- [ ] **技术栈**: Python、Rust、Go、TypeScript/JavaScript
- [ ] **项目规模**: 中型（100+ 文件）至超大型（10000+ 文件）
