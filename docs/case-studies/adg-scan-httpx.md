# ADG 扫描在 httpx 上的实战验证

## 背景与挑战

**项目目标**: 验证 ADG（AI Developer Governance）规则引擎在真实开源项目上的有效性，以 httpx（现代 HTTP 客户端库，14k+ Star）为测试对象。

**核心挑战**:
1. httpx 代码库虽小（23 个核心文件），但使用了大量现代 Python 特性（类型注解、async/await、泛型），可能触发大量类型相关规则
2. 需要区分真实问题与误报，特别是 import 位置、__all__ 缺失、Any 类型使用等风格性问题
3. 验证 ADG 的 exclude_patterns 机制能否正确过滤测试文件误报

**约束条件**:
- 不修改 httpx 源码，仅运行扫描并分析结果
- 对比本项目（已全量修复）与 httpx（原始代码）的质量门禁差异

## AI 协作过程

### Phase 1: 需求分析 & PRD
- **人**: 选定 httpx 作为验证目标，定义验收标准（通过率、error 数量、问题密度）
- **AI**: 分析 httpx 代码库结构、文件数、依赖关系，生成预期问题分布
- **验证方式**: 对比预期与实际扫描结果
- **耗时对比**: 传统 1 小时 → AI 协作 15 分钟

### Phase 2: 架构设计 & 契约定义
- **人**: 定义对比维度（通过率、平均问题/文件、Error 级别数量）
- **AI**: 设计对比表格模板、生成扫描命令脚本
- **验证方式**: 试运行扫描确认输出格式
- **耗时对比**: 传统 2 小时 → AI 协作 30 分钟

### Phase 3: 迭代编码 (TDD 循环)
- **循环次数**: 3 次（初始扫描 → 规则调整 → 复测验证）
- **典型循环**: `adg scan httpx` → 解析 749 error → 分析误报模式 → 调整 exclude_patterns/白名单 → 重新扫描
- **关键 Bug/挑战**:
  - import 位置不规范触发 py-import-position (200+ 处)
  - 缺失 `__all__` 触发 py-missing-all (150+ 处)
  - 大量 `Any` 类型触发 py-any-type (300+ 处)
  - 测试文件误报需 exclude_patterns 过滤
- **修复方式**: 实现 exclude_patterns 引擎、py-nested-import 排除 TYPE_CHECKING、py-missing-all 去重、common-hardcoded-secret 白名单

### Phase 4: 优化 & 交付
- **人**: 撰写验证报告、整理规则效率对比、制定引擎改进路线图
- **AI**: 生成问题分布统计、计算修复降幅、生成对比图表
- **最终验收**: httpx 扫描 error 从 749 降至 207（72% 降幅），验证 exclude_patterns 机制有效

## 关键洞察

### 1. 小项目也能暴露大量规则问题
httpx 仅 23 个核心文件却产生 749 个 error，平均每文件 32.6 个问题。说明现代 Python 项目普遍存在 import 规范、类型注解完整性、导出控制等系统性问题。

### 2. exclude_patterns 是大规模采用的关键
测试文件占 httpx 问题的 60%+。实现 exclude_patterns 后，单次配置即可过滤所有测试目录误报，这是规则引擎走向生产可用的关键一步。

### 3. 类型注解规则需分级严重度
`py-any-type` 产生 300+ 个 warning，但大多是库代码为了泛型兼容不得不使用 Any。建议将此类规则降级为 info 或提供白名单机制。

### 4. __all__ 缺失反映模块设计松散
150+ 个 py-missing-all 表明多数模块未显式定义公开 API。这在库开发中是真实的可维护性风险。

### 5. 规则改进的 ROI 来自"高频真实问题"
72% 的问题降幅主要来自 4 项改进：exclude_patterns（过滤测试误报）、TYPE_CHECKING 排除（消除类型注解误报）、去重（合并同一文件重复问题）、白名单（硬编码密钥例外）。这 4 项覆盖了 80%+ 的误报。
