# AI 代码生成质量标准 (AI Code Generation Quality)

> AI 生成的代码不等于可信赖的代码。必须建立系统化的质量验证框架。

---

## 1. 概述

AI 代码生成的根本挑战：**AI 不理解代码的语义，它只是生成统计上最可能的下一个 AI 生成的代码可能在语法上正确、在逻辑上错误。

本标准定义了从 **生成 → 验证 → 交付** 全过程的质量控制要求。

### 适用范围

- 所有 AI 辅助生成的代码
- AI 自动补全的代码
- AI Agent 自主生成的代码
- AI 代码

---

## 2. AI 幻觉分类 (Hallucination Taxonomy)

### 2.1 幻觉类型

| 类型 | 描述 | 风险等级 | 检测难度 |
|------|------|----------|----------|
| **API 幻觉** | 调用不存在的 API 或方法 | 🔴 高 | 低 (编译/类型检查) |
| **逻辑幻觉** | 代码逻辑与需求不符 | 🔴 高 | 高 (需人工审查) |
| **数据幻觉** | 使用错误的数据类型或格式 | 🟡 中 | 中 (测试可捕获) |
| **依赖幻觉** | 引用不存在的库或版本 | 🟡 中 | 低 (安装时报错) |
| **安全幻觉** | 引入安全漏洞 | 🔴 高 | 高 (需安全扫描) |
| **性能幻觉** | 生成低效的算法或实现 | 🟡 中 | 中 (需性能测试) |
| **一致性幻觉** | 违反项目约定或风格 | 🟢 低 | 低 (Linter 可捕获) |

### 2.2 幻觉产生模式

```
模式 1: 训练数据过时
  AI 学到的是旧版 API → 生成过时代码
  预防: 在 Prompt 中提供当前 API 文档

模式 2: 上下文不足
  AI 不了解项目约定 → 生成不符合风格的代码
  预防: 提供代码规范 + 示例

模式 3: 过度泛化
  AI 将相似但不同的需求混淆 → 生成不精确的代码
  预防: 提供精确的需求描述 + 边界条件

模式 4: 自信地错误
  AI 对不确定的代码不表现出犹豫 → 生成看似正确但有 Bug 的代码
  预防: 强制输出置信度 + 多次生成对比
```

## 3. 质量控制流程

### 3.1 生成阶段 (Prompt Engineering)

**必须满足的 Prompt 要求**:

| 要素 | 要求 | 示例 |
|------|------|------|
| **意图明确** | 一句话说明要做什么 | "实现一个带缓存的用户查询函数" |
| **约束明确** | 指定语言/框架/版本 | "Python 3.12, FastAPI 0.115" |
| **边界明确** | 指定输入/输出/异常 | "输入 user_id, 返回 User, 找不到抛 UserNotFoundError" |
| **示例提供** | 提供期望的输入/输出 | "例: get_user(1) → User(id=1, name='Alice')" |
| **约束排除** | 指定不要什么 | "不要使用 ORM, 使用原生 SQL" |

### 3.2 验证阶段 (三级验证)

```
Level 1: 自动化验证 (零人工)
  ├── 编译/类型检查 → 捕获 API 幻觉、语法错误
  ├── Linter → 捕获一致性幻觉
  ├── 单元测试 → 捕获逻辑幻觉 (已有测试覆盖的部分)
  └── 安全扫描 → 捕获安全幻觉

Level 2: 半自动验证 (少量人工)
  ├── 代码审查 → 捕获逻辑幻觉、设计幻觉
  ├── 集成测试 → 捕获接口不匹配
  └── 性能测试 → 捕获性能幻觉

Level 3: 深度验证 (人工主导)
  ├── 逻辑审查 → 捕获复杂业务逻辑错误
  ├── 安全审查 → 捕获深层安全漏洞
  └── 架构审查 → 捕获设计偏差
```

### 3.3 交付阶段

| 检查项 | 方法 | 通过标准 |
|--------|------|----------|
| 所有自动化检查通过 | CI/CD | 0 errors, 0 critical warnings |
| 代码覆盖率 | coverage 报告 | 核心逻辑 ≥ 80% |
| 无已知反模式 | 反模式检测 | 0 反模式命中 |
| 变更可追溯 | git blame | 每个变更可追溯到需求 |

## 4. 幻觉检测方法

### 4.1 静态检测工具组合

| 语言 | Linter | 类型检查 | 安全扫描 | 可捕获幻觉 |
|------|--------|----------|----------|------------|
| Python | ruff | mypy | bandit | API/一致性/安全 |
| TypeScript | eslint | tsc | npm audit | API/一致性/依赖 |
| Rust | clippy | rustc | cargo audit | API/一致性/安全 |
| Go | golangci-lint | go vet | govulncheck | API/一致性/安全 |
| Java | checkstyle | javac | spotbugs | API/一致性/安全 |

### 4.2 动态检测策略

```python
DYNAMIC_CHECKS = {
    "unit_test": "验证每个函数的输入/输出正确性",
    "integration_test": "验证模块间交互正确性",
    "property_test": "验证代码满足不变量",
    "fuzz_test": "验证代码对异常输入的鲁棒性",
    "regression_test": "验证修改不引入新 Bug",
}
```

### 4.3 人工审查重点 (按优先级)

| 优先级 | 审查内容 | 为什么重要 |
|--------|----------|------------|
| **P0** | 认证/授权逻辑 | 安全关键 |
| **P0** | 输入验证/输出编码 | 防注入 |
| **P0** | 数据加密/脱敏 | 合规要求 |
| **P1** | 核心业务逻辑 | 功能正确性 |
| **P1** | 错误处理路径 | 健壮性 |
| **P2** | API 接口定义 | 契约 |
| **P2** | 数据模型 | 一致性 |
| **P3** | 性能关键路径 | 效率 |

## 5. AI 代码标注规范

### 5.1 标注格式

AI 生成的代码必须在文件头添加标注注释：

```python
# [AI-GEN] Generated by AI, reviewed by human
# Model: Claude-4 / Date: 2026-07-22
# Reviewer: @reviewer / Review Date: 2026-07-22
# Test Coverage: 85% / Known Limitations: concurrent scenarios


def process_payment(amount: Decimal, user_id: str) -> PaymentResult:
    """处理支付"""
    ...
```

### 5.2 标注必要性矩阵

| 场景 | 是否标注 | 原因 |
|------|----------|------|
| AI 生成新函数 | ✅ 必须 | 可追溯性 |
| AI 自动补全单行 | ❌ 不需要 | 过于细碎 |
| AI 重构代码 | ✅ 必须 | 行为变更风险 |
| AI 修复 Bug | ✅ 必须 | 回归风险 |
| AI 生成测试 | ❌ 不需要 | 测试本身是验证 |
| AI 生成文档 | ❌ 不需要 | 无运行时风险 |

## 6. 持续改进机制

### 6.1 幻觉统计指标

每个 Sprint 结束时统计：

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| **幻觉率** | 幻觉数 / AI 生成代码行数 | < 5% |
| **幻觉检出率** | 自动检出数 / 总幻觉数 | > 80% |
| **幻觉逃逸率** | 生产环境发现的幻觉数 | = 0 |
| **平均修复时间** | 发现到修复的平均时间 | < 4 小时 |
