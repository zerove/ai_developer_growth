# AI 开发全生命周期标准 (AI-SDLC)

> AI 不是取代开发流程，而是重新定义每个阶段的角色和质量标准。

---

## 1. 概述

传统 SDLC 在 AI 时代需要重构。本标准定义了 **7 个阶段** 中 AI 与人类的协作模式、质量门禁和交付物要求。

### AI-SDLC 与传统 SDLC 的区别

| 维度 | 传统 SDLC | AI-SDLC |
|------|-----------|---------|
| **需求分析** | 人工编写 PRD | AI 辅助生成 + 人工审查 |
| **设计** | 人工架构设计 | AI 建议方案 + 人工决策 |
| **实现** | 人工编码 | AI 生成 + 人工审查验证 |
| **测试** | 人工编写测试 | AI 生成测试 + 人工设计策略 |
| **部署** | 人工/CI/CD | AI 辅助配置 + 自动化部署 |
| **维护** | 人工 Bug 修复 | AI 辅助定位 + 人工修复 |
| **监控** | 人工分析日志 | AI 异常检测 + 人工决策 |

## 3. 阶段详解

### 阶段 1: 需求分析

**AI 角色**: 产品经理助手
**人类角色**: 最终决策者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 需求收集 | 整理碎片化需求 | 确认优先级 | 需求列表 |
| PRD 生成 | 生成结构化 PRD | 审查+修改 | PRD 文故事 | 生成用户故事 | 验证完整性 | User Stories |
| 边界条件 | 列举边界情况 | 确认处理策略 | 边界条件表 |
| 技术可行性 | 评估技术方案 | 最终决策 | 可行性报告 |

**质量门禁**:
- [ ] PRD 包含完整的用户故事
- [ ] 边界条件已列举并有处理策略
- [ ] 技
- [ ] 优先级已确认

**Prompt 模板**:
```
我需要实现 [功能描述]。

请帮我生成 PRD，包含:
1. 用户故事 (As a... I want... So that...)
2. 功能矩阵 (功能点 + 优先级 + 复杂度)
3. 边界条件 (输入限制、异常场景、并发场景)
4. 非功能需求 (性能、安全、可用性)
5. 技术约束 (语言、框架、依赖)
```

---

### 阶段 2: 架构设计

**AI 角色**: 架构师助手
**人类角色**: 架构决策者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 方案生成 | 生成多个设计方案 | 选择最优方案 | 设计方案 |
| 架构图 | 生成架构描述 | 审查+调整 | 架构图 |
| 数据模型 | 设计数据结构 | 确认模型 | 数据模型 |
| 接口定义 | 生成 API 契约 | 审查+修改 | API 文档 |
| ADR 生成 | 起草决策记录 | 审批 | ADR 文档 |

**质量门禁**:
- [ ] 至少 2 个备选方案
- [ ] 架
- [ ] 数据模型完整
- [ ] API 契约明确
- [ ] ADR 记录了决策理由

**Prompt 模板**:以下需求，设计系统架构:

需求: [PRD 摘要]
约束: [技术约束]

请提供:
1. 2-3 个备选架构方案 (含优缺点对比)
2. 推荐方案的详细设计
3. 数据模型 (ER 图描述)
4. 核心 API 接口定义
5. 关键技术决策 (ADR 格式)
```

---

### 阶段 3: 实现编码

**AI 角色**: 代码生成器
**人类角色**: 代码审查者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 代码生成 | 生成函数/模块代码 | 审查+修改 | 源代码 |
| 单元测试 | 生成测试用例 | 审查测试策略 | 测试代码 |
| 文档生成 | 生成代码注释 | 审查+补充 | 文档 |
| 重构建议 | 分析代码质量 | 决定是否重构 | 重构方案 |

**质量门禁**:
- [ ] Linter 检查通过 (0 errors)
- [ ] 类型检查通过 (0 errors)
- [ ] 单元测试通过 (100%)
- [ ] 测试覆盖率 ≥ 80%
- [ ] 代码审查通过
- [ ] 无硬编码密钥
- [ ] 错误处理完整

**AI 代码生成规范**:
```python
# 必须提供给 AI 的上下文:
1. 接口定义 (函数签名 + 类型)
2. 依赖的现有代码 (相关函数)
3. 项目编码规范 (linting 规则)
4. 测试示例 (已有测试风格)

# AI 生成后必须:
1. 运行 Linter 修复风格问题
2. 运行类型检查修复类型错误
3. 运行测试验证功能正确
4. 人工审查逻辑正确性
```

---

### 阶段 4: 测试验证

**AI 角色**: 测试生成器
**人类角色**: 测试策略师

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 测试用例生成 | 生成单元/集成测试 | 设计测试策略 | 测试代码 |
| 边界测试 | 生成边界条件测试 | 确认关键场景 | 边界测试 |
| 回归测试 | 生成回归测试 | 归测试 |
| 测试报告 | 生成测试报告 | 审查+决策 | 测试报告 |

**质量门禁**:
- [ ] 所有测试通过
- [ ] 覆盖率达标 (核心逻辑 ≥ 80%)
- [ ] 边界条件已覆盖
- [ ] 无 flaky tests
- [ ] 性能测试通过 (如需要)

**AI 测试生成策略**:
```
Level 1: AI 自动生成
  - 正常路径测试
  - 常见边界测试
  - 类型检查测试

Level 2: AI 生成 + 人工补充
  - 业务逻辑边界测试
  - 并发场景测试
  - 安全相关测试

Level 3: 人工设计 + AI 实现
  - 关键业务场景测试
  - 端到端测试
  - 性能/压力测试
```

---

### 阶段 5: 部署上线

**AI 角色**: 部署助手
**人类角色**: 部署决策者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 配置生成 | 生成部署配置 | 审查+修改 | 配置文件 |
| CI/CD 配置 | 生成流水线配置 | 审查+激活 | CI/CD 配置 |
| 发布说明 | 生成 changelog | 审查+发布 | Release Notes |
| 回滚方案 | 生成回滚步骤 | 确认+执行 | 回滚文档 |

**质量门禁**:
- [ ] 部署配置已审查
- [ ] CI/CD 流水线通过
- [ ] 回滚方案已准备
- [ ] 监控已配置
- [ ] 告警规则已设置

---

### 阶段 6: 监控运维

**AI 角色**: 异常检测器
**人类角色**: 运维决策者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| 日志分析 | 分析异常模式 | 决定处理方案 | 分析报告 |
|检测性能退化 | 优化决策 | 性能报告 |
| 告警处理 | 初步分类告警 | 处理关键告警 | 处理记录 |
| 容量规划 | 预测资源需求 | 审批扩容 | 规划报告 |

---

### 阶段 7: 维护迭代

**AI 角色**: Bug 定位助手
**人类角色**: 修复决策者

| 步骤 | AI 负责 | 人类负责 | 交付物 |
|------|---------|----------|--------|
| Bug 分析 | 分析错误日志 | 确认根因 | 分析报告 |
| 修复建议 | 生成修复方案 | 选择最优方案 | 修复方案 |
| 代码修复 | 生成修复代码 | 审查+测试 | 修复代码 |
| 文档更新 | 更新相关文档
- [[GOVERNANCE|通用治理标准]]
- [[GOVERNANCE|通用治理标准]] | 审查 | 更新文档 |

## 4. 质量门禁总览

```
Gate 0: 需求审查     → PRD + 用户故事 + 边界条件
Gate 1: 设计审查     → 架构方案 + 数据模型 + API 定义
Gate 2: 实现审查     → 代码 + 测试 + Linter + 类型检查
Gate 3: 测试审查     → 测试报告 + 覆盖率 + 边界覆盖
Gate 4: 部署审查     → 配置 + CI/CD + 回滚方案
Gate 5: 上线审查     → 监控 + 告警 + 回滚就绪
```

## 5. AI 使用规范

### 5.1 必须使用 AI 的场景

| 场景 | 原因 |
|------|------|
| 重复性代码生成 | 效率提升 3-5x |
| 测试用例生成 | 覆盖率提升 2-3x |
| 文档生成 | 一致性保障 |
| 代码审查辅助 | 漏检率降低 40% |
| Bug 定位 | 定位时间缩短 50% |

### 5.2 禁止使用 AI 的场景

| 场景 | 原因 |
|------|------|
| 安全关键代码的最终审查 | 需要人工确认 |
| 架构决策的最终拍板 | 需要人类判断 |
| 用户隐私相关逻辑 | 合规要求 |
| 法律/合规相关代码 | 法律责任 |

### 5.3 AI 使用红线

- ❌ 不得将 AI 生成的代码未经审查直接部署到生产
- ❌ 不得将敏感数据/密钥发送给 AI 模型
- ❌ 不得完全依赖 AI 的安全建议
- ❌ 不得用 AI 替代安全审计

## 6. 度量指标

### 6.1 过程指标

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| AI 辅助率 | AI 参与的任务数 / 总任务数 | > 60% |
| AI 采纳率 | 采纳 AI 建议数 / AI 建议总数 | > 70% |
| 审查通过率 | AI 代码一次审查通过数 / AI 代码总数 | > 50% |
| 返工率 | AI 代码需返工数 / AI 代码总数 | < 20% |

### 6.2 质量指标

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| Bug 密度 | Bug 数 / 千行代码 | < 1 | 80% |
| 安全漏洞数 | 生产环境漏洞数 | = 0 |
| 生产事故数 | 生产环境事故数 / 月 | < 2 |

### 6.3 效率指标

| 指标 | 计算方式 | 目标 |
|------|----------|------|
| 开发速度提升 | 有AI/无AI 完成时间比 | > 1.5x |
| 代码审查时间 | 平均审查时间/PR | < 1 小时 |
| Bug 修复时间 | 平均修复时间/Bug | < 4 小时 |
| 部署频率 | 部署次数/周 | > 3 |
