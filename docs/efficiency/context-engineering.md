# 上下文工程与 AI 输出验证 (Context Engineering & AI Output Verification)

> 精准传递意图，系统化验证结果。

---

## 概述

AI 编程的核心挑战不在于"生成代码"，而在于**精准传递上下文**和**系统化验证输出**。本文档提供从上下文管理到验证方法论的完整框架。

---

## 1. 上下文工程 (Context Engineering)

### 1.1 核心原则

**最小上下文原则**：只提供实现当前任务所需的最小信息集。

| 信息类型 | 何时提供 | 示例 |
|----------|----------|------|
| **代码片段** | 修改特定函数时 | 函数定义 + 调用者 |
| **接口定义** | 实现新功能时 | API 契约 + 数据模型 |
| **架构文档** | 设计决策时 | 系统架构图 + ADR |
| **历史记录** | 调试问题时 | 错误日志 + 最近提交 |
| **测试用例** | 修复 Bug 时 | 失败测试 + 预期行为 |

### 1.2 上下文分层策略

```
Layer 1: 项目全局上下文
├── README.md (项目定位)
├── CONTEXT.md (当前状态)
└── ADR/ (架构决策)

Layer 2: 模块级上下文
├── 模块接口定义
├── 数据模型
└── 依赖关系

Layer 3: 任务级上下文
├── 具体代码片段
├── 测试用例
└── 错误日志
```

### 1.3 上下文传递技巧

**精准引用**：
```markdown
# 差：模糊描述
"修改用户认证逻辑"

# 好：精准引用
"修改 src/auth/login.ts 中的 validateToken 函数，
需要处理 token 过期的情况，
参考 src/auth/types.ts 中的 Token 接口定义"
```

**分层传递**：
```markdown
# 先给高层架构
"这是一个电商系统，使用微服务架构，
用户服务负责认证和授权"

# 再给具体实现
"现在需要在 UserService 中添加 OAuth2 支持，
参考 src/auth/oauth2.ts 中的 OAuth2Client 类"
```

### 1.4 上下文窗口优化

**策略 1: 摘要替代全文**
```markdown
# 差：粘贴整个文件 (1000 行)
[完整文件内容]

# 好：提供摘要 + 关键片段
"User 模型定义了 5 个字段：id, name, email, password, createdAt。
现在需要添加 phone 字段，
参考 UserCreate schema 在 src/schemas/user.ts 中的定义"
```

**策略 2: 引用而非复制**
```markdown
# 差：复制代码
[粘贴 100 行代码]

# 好：引用代码位置
"参考 src/services/user.ts 第 45-80 行的 UserService 类，
需要添加一个新方法 validatePhone"
```

**策略 3: 增量上下文**
```markdown
# 第 1 轮：基础上下文
"这是一个用户注册函数，需要添加邮箱验证"

# 第 2 轮：基于反馈的增量上下文
"上一轮的实现缺少边界情况处理，
请添加：空邮箱、无效格式、已存在邮箱的处理"
```

## 2. AI 输出验证方法论

### 2.1 验证策略金字塔

```
           ┌─────────────────┐
           │   手动验证      │  ← 最高成本，最低频率
           │  (关键路径)     │
           ├─────────────────┤
           │   集成测试      │  ← 中等成本，中等频率
           │  (模块交互)     │
           ├─────────────────┤
           │   单元测试      │  ← 最低成本，最高频率
           │  (函数级别)     │
           └─────────────────┘
```

### 2.2 分层验证策略

**Layer 1: 语法验证 (自动)**
```bash
# LSP 诊断 - 类型错误、语法错误
npx tsc --noEmit

# Linter - 代码风格、潜在问题
npx eslint src/ --ext .ts

# 编译检查
npm run build
```

**Layer 2: 单元测试 (自动)**
```bash
# 运行所有测试
npm test

# 运行特定测试文件
npm test -- --testPathPattern=user-service

# 覆盖率报告
npm test -- --coverage
```

**Layer 3: 集成测试 (自动)**
```typescript
// API 契约测试示例
describe('User API Contract', () => {
  it('POST /api/users should return 201 with valid data', async () => {
    const response = await request(app)
      .post('/api/users')
      .send({ email: 'test@example.com', name: 'Test User' });
    
    expect(response.status).toBe(201);
    expect(response.body).toHaveProperty('id');
    expect(response.body.email).toBe('test@example.com');
  });
});
```

**Layer 4: 手动验证 (人工)**
- 业务逻辑正确性
- 用户体验验证
- 性能基准测试

### 2.3 自信度校准

**高自信度 (可直接采纳)**：
- ✅ 语法检查通过
- ✅ 单元测试全部通过
- ✅ 代码风格符合规范
- ✅ 逻辑清晰易懂

**中自信度 (需人工审查)**：
- ⚠️ 涉及核心业务逻辑
- ⚠️ 涉及安全相关代码
- ⚠️ 涉及性能关键路径
- ⚠️ 涉及数据一致性

**低自信度 (需重写或深度审查)**：
- ❌ 测试覆盖率 < 80%
- ❌ 代码复杂度过高
- ❌ 缺少错误处理
- ❌ 无法向别人解释

## 3. 验证检查清单

### 3.1 代码生成后检查

```markdown
## AI 生成代码验证清单

### 语法层面
- [ ] LSP 无错误
- [ ] Linter 无警告
- [ ] 编译通过

### 逻辑层面
- [ ] 业务逻辑正确
- [ ] 边界情况处理
- [ ] 错误处理完善

### 测试层面
- [ ] 单元测试通过
- [ ] 覆盖率 > 80%
- [ ] 边界测试包含

### 安全层面
- [ ] 无安全漏洞
- [ ] 输入验证完整
- [ ] 敏感信息保护

### 性能层面
- [ ] 无明显性能问题
- [ ] 数据库查询优化
- [ ] 内存使用合理
```

### 3.2 调试验证流程

```
1. 复现问题
   └── 编写失败测试用例

2. 分析原因
   └── 代码审查 + 日志分析

3. 实施修复
   └── 最小化修改

4. 验证修复
   ├── 测试通过
   ├── 回归测试通过
   └── 手动验证

5. 记录总结
   └── 更新测试用例 + 文档
```

## 4. 真实案例

### 案例 1: 上下文管理优化

**背景**: 某 SaaS 产品团队在开发新功能

**问题**: AI 生成的代码频繁出错，需要多次修正

**分析**:
- 上下文混乱：多个功能混在同一个会话
- 信息过载：粘贴了整个文件，AI 无法聚焦
- 缺少验证：没有测试就直接上线

**解决方案**:
1. 每个功能开启新的 Chat Session
2. 使用精准引用，只提供必要上下文
3. 建立验证流程：测试 → 审查 → 上线

**效果**: 代码出错率降低 60%

### 案例 2: 验证流程优化

**背景**: 某金融科技公司支付模块

**问题**: AI 生成的代码上线后出现资金计算错误

**分析**:
- 缺少边界测试
- 没有进行安全审查
- 直接上线，没有验证流程

**解决方案**:
1. 建立验证检查清单
2. 关键路径必须人工审查
3. 强制测试覆盖

**效果**: 生产事件减少 80%
