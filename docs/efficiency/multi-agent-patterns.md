# 多 Agent 编排模式 (Multi-Agent Orchestration Patterns)

> 从单兵作战到团队协作。

---

## 概述

当单个 Agent 无法高效完成复杂任务时，**多 Agent 编排**成为必然选择。本文档提供从单 Agent 到多 Agent 的演进路径，以及各种编排模式的适用场景。

---

## 1. Agent 类型定义

### 1.1 基础 Agent 类型

| Agent 类型 | 职责 | 能力 | 成本 |
|------------|------|------|------|
| **Explore** | 代码搜索、模式发现 | grep、文件读取 | 低 |
| **Librarian** | 外部知识检索 | 文档搜索、API 查询 | 低 |
| **Oracle** | 架构咨询、复杂推理 | 只读、高 IQ | 高 |
| **Plan** | 任务分解、计划制定 | 只读、不可编辑 | 高 |
| **Build** | 代码实现、文件编辑 | 读写、执行 | 中 |
| **Test** | 测试执行、质量验证 | 测试框架、断言 | 中 |

### 1.2 Agent 能力矩阵

```
           读取  写入  执行  推理  搜索
Explore     ✅   ❌   ❌   ✅   ✅
Librarian   ✅   ❌   ❌   ✅   ✅
Oracle      ✅   ❌   ❌   ✅   ✅
Plan        ✅   ❌   ❌   ✅   ✅
Build       ✅   ✅   ✅   ✅   ❌
Test        ✅   ❌   ✅   ✅   ❌
```

## 2. 编排模式

### 2.1 模式 1: 串行流水线 (Sequential Pipeline)

**适用场景**: 任务有明确的前后依赖关系

```
Explore → Plan → Build → Test
```

**示例**: 新功能开发
```
1. Explore: 搜索现有代码模式
2. Plan: 设计实现方案
3. Build: 编写代码
4. Test: 验证功能
```

**优点**:
- 简单易懂
- 错误易于定位
- 上下文清晰

**缺点**:
- 速度慢（串行执行）
- 无法并行优化
- 单点故障

---

### 2.2 模式 2: 并行扇出 (Parallel Fan-Out)

**适用场景**: 多个独立子任务可并行执行

```
        ┌→ Build (模块 A) ─┐
Plan ──┤→ Build (模块 B) ─├→ Test
        └→ Build (模块 C) ─┘
```

**示例**: 微服务开发
```
1. Plan: 设计服务边界
2. 并行 Build:
   - Agent 1: 用户服务
   - Agent 2: 订单服务
   - Agent 3: 支付服务
3. Test: 集成测试
```

**优点**:
- 速度快（并行执行）
- 资源利用率高
- 可扩展性强

**缺点**:
- 复杂度高
- 冲突解决困难
- 上下文同步挑战

---

### 2.3 模式 3: 主从模式 (Master-Slave)

**适用场景**: 有明确的协调者和执行者

```
Master (Plan) ──┬→ Slave 1 (Build)
                ├→ Slave 2 (Build)
                └→ Slave 3 (Test)
```

**示例**: 代码重构
```
1. Master: 分析代码，制定重构计划
2. Slaves: 并行执行重构任务
3. Master: 汇总结果，验证一致性
```

**优点**:
- 职责清晰
- 协调简单
- 错误隔离

**缺点**:
- Master 成为瓶颈
- Slave 自主性低
- 扩展性受限

---

### 2.4 模式 4: 对等协作 (Peer-to-Peer)

**适用场景**: 需要多角度分析和辩论

```
Agent A ←→ Agent B
  ↕           ↕
Agent C ←→ Agent D
```

**示例**: 架构设计评审
```
1. Agent A: 提出架构方案
2. Agent B: 质疑方案可行性
3. Agent C: 提出替代方案
4. Agent D: 评估各方案优劣
5. 综合: 选择最佳方案
```

**优点**:
- 多角度分析
- 减少偏见
- 提高质量

**缺点**:
- 协调复杂
- 可能陷入辩论
- 决策缓慢

---

### 2.5 模式 5: 层级模式 (Hierarchical)

**适用场景**: 大型项目，需要分层管理

```
CEO (Master Agent)
├── CTO (Tech Lead Agent)
│   ├── Frontend Agent
│   └── Backend Agent
└── QA (Quality Agent)
    ├── Test Agent
    └── Review Agent
```

**示例**: 完整产品开发
```
1. CEO: 定义产品需求
2. CTO: 技术架构设计
3. Frontend: UI 实现
4. Backend: API 实现
5. QA: 质量验证
```

**优点**:
- 职责清晰
- 可扩展性强
- 适合大型项目

**缺点**:
- 层级复杂
- 沟通成本高
- 响应速度慢

## 3. 选择指南

### 3.1 决策树

```
任务复杂度？
├─ 简单（单文件修改）→ 单 Agent
├─ 中等（多文件协作）→ 串行流水线
└─ 复杂（多模块协作）
   ├─ 模块独立？ → 并行扇出
   ├─ 需要协调？ → 主从模式
   ├─ 需要辩论？ → 对等协作
   └─ 大型项目？ → 层级模式
```

### 3.2 场景匹配

| 场景 | 推荐模式 | 理由 |
|------|----------|------|
| **Bug 修复** | 串行流水线 | 流程清晰，易于定位 |
| **新功能开发** | 并行扇出 | 模块独立，可并行 |
| **代码重构** | 主从模式 | 需要统一协调 |
| **架构设计** | 对等协作 | 需要多角度分析 |
| **完整产品** | 层级模式 | 需要分层管理 |
| **代码审查** | 对等协作 | 需要多视角检查 |
| **测试生成** | 并行扇出 | 测试用例独立 |

## 4. 实施最佳实践

### 4.1 上下文管理

**共享上下文**:
```markdown
# CONTEXT.md
## 项目状态
- 当前模块: 用户服务
- 已完成: 认证、授权
- 进行中: 用户资料管理

## 架构决策
- 使用 REST API
- 数据库: PostgreSQL
- 缓存: Redis

## 代码规范
- 函数长度 < 50 行
- 测试覆盖率 > 80%
```

**隔离上下文**:
```markdown
# Agent A 的上下文
- 任务: 实现用户注册
- 依赖: User 模型
- 输出: /src/auth/register.ts

# Agent B 的上下文
- 任务: 实现用户登录
- 依赖: User 模型
- 输出: /src/auth/login.ts
```

### 4.2 冲突解决

**文件冲突**:
- 使用 Git 分支隔离
- 合并前进行代码审查
- 冲突自动检测和提示

**逻辑冲突**:
- 定义清晰的接口契约
- 使用类型系统约束
- 集成测试验证

**资源冲突**:
- 限制并发 Agent 数量
- 使用锁机制
- 资源池管理

### 4.3 错误处理

**Agent 失败**:
```
1. 记录错误信息
2. 通知 Master Agent
3. 决策：重试 / 跳过 / 人工介入
4. 记录失败原因
5. 更新任务状态
```

**级联失败**:
```
1. 检测失败 Agent
2. 隔离失败模块
3. 通知相关 Agent
4. 降级处理
5. 人工恢复
```

## 5. 真实案例

### 案例 1: 某 SaaS 产品多 Agent 开发

**背景**: 开发一个新的数据分析模块

**模式选择**: 并行扇出

**执行**:
1. Plan Agent: 设计模块架构
2. 并行 Build Agents:
   - Agent 1: 数据采集模块
   - Agent 2: 数据处理模块
   - Agent 3: 可视化模块
3. Test Agent: 集成测试

**效果**:
- 开发时间: 2 周 → 3 天 (5x 提升)
- 代码质量: 测试覆盖率 85%
- 成本: Token 消耗减少 40%

### 案例 2: 某金融机构代码重构

**背景**: 重构遗留支付系统

**模式选择**: 主从模式

**执行**:
1. Master Agent: 分析代码，制定重构计划
2. Slave Agents: 并行执行重构任务
3. Master Agent: 汇总结果，验证一致性

**效果**:
- 重构时间: 1 个月 → 1 周 (4x 提升)
- 回滚率: 从 30% 降至 5%
- 代码质量: 复杂度降低 60%

## 模式选择速查

| 场景 | 推荐模式 |
|------|----------|
| Bug 修复 | 串行流水线 |
| 新功能开发 | 并行扇出 |
| 代码重构 | 主从模式 |
| 架构设计 | 对等协作 |

**核心原则**: 简单优先，能用单 Agent 就不用多 Agent。
