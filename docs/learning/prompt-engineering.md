# 结构化 Prompt 工程指南 (Structured Prompt Engineering)

在 AI 时代，**Prompt 就是新的编程语言**。掌握结构化 Prompt 技能，能够将 LLM 的输出从"随机的灵感"提升为"可复现的工程产出"。

## 核心原则

### 1. 明确性 (Clarity)
**坏 Prompt**: "帮我写个函数"
**好 Prompt**: "用 Python 编写一个函数 `parse_config(path: str) -> dict`，读取 YAML 配置文件并返回字典，处理文件不存在和格式错误的异常"

### 2. 结构化 (Structure)
使用 Markdown 格式组织 Prompt，让 LLM 清晰理解你的意图：

```markdown
## 任务
实现一个 REST API 端点

## 要求
- 方法: POST /api/users
- 输入: JSON body 包含 name (string), email (string)
- 输出: 创建的用户对象 + 201 状态码
- 验证: email 格式校验

## 约束
- 使用 FastAPI
- 必须有类型注解
- 包含 docstring
```

### 3. 上下文 (Context)
提供足够的背景信息：

```markdown
## 项目背景
这是一个电商后端项目，使用 Python 3.11 + FastAPI + SQLAlchemy

## 现有代码
- models/user.py: 已有 User 模型
- schemas/user.py: 已有 UserCreate schema

## 你的任务
在 routers/user.py 中实现创建用户的端点
```

## 高级技巧

### Chain-of-Thought (CoT) - 思维链

让 LLM 展示推理过程，特别适合复杂逻辑：

```markdown
请分析以下代码的性能问题，并给出优化建议。

**请按以下步骤分析：**
1. 首先识别代码中的时间复杂度
2. 找出可能的瓶颈点
3. 提出具体的优化方案
4. 解释每个优化的原理

[代码片段]
```

**进阶: Self-Consistency CoT**
```markdown
对于这个问题，请给出 3 种不同的解法，然后评估哪种最优：

问题: [具体问题]

请分别用：
- 方法 A: [某种方法]
- 方法 B: [另一种方法]  
- 方法 C: [第三种方法]

最后给出你的推荐并解释理由。
```

### Few-Shot Learning - 少样本学习

通过示例教会 LLM 你想要的格式：

```markdown
请将用户评论分类为正面/负面/中性。

**示例：**

评论: "这个产品太棒了，推荐给所有人！"
分类: 正面

评论: "质量一般，不值这个价格"
分类: 负面

评论: "还行吧，凑合能用"
分类: 中性

**现在请分类：**
评论: "发货很快，包装也很好，下次还会购买"
分类:
```

### Structured Output - 结构化输出

强制 LLM 输出特定格式：

```markdown
请分析这段代码并以 JSON 格式返回结果。

**输出格式：**
{
  "issues": [
    {
      "type": "bug|warning|info",
      "line": <行号>,
      "description": "<问题描述>",
      "suggestion": "<修复建议>"
    }
  ],
  "summary": "<总体评价>"
}

**代码：**
[代码片段]
```

### Role Prompting - 角色设定

```markdown
你是一位有 10 年经验的 Python 高级工程师，专注于性能优化和代码质量。

请以这个身份审查以下代码：
- 关注点：性能、可维护性、Python 惯用写法
- 风格：直接、技术性强、给出具体代码示例

[代码片段]
```

## 实战模板

### 模板 1: 代码审查

```markdown
## 角色
资深代码审查者

## 任务
审查以下代码变更

## 审查维度
1. 正确性: 逻辑是否正确？
2. 性能: 有无性能问题？
3. 安全性: 有无安全隐患？
4. 可维护性: 代码是否清晰易懂？

## 输出格式
| 问题 | 严重程度 | 位置 | 建议 |
|------|----------|------|------|
| ...  | 高/中/低 | 行号 | 具体建议 |

## 代码变更
[diff 或代码片段]
```

### 模板 2: 架构设计

```markdown
## 背景
[项目背景描述]

## 需求
[功能需求]

## 约束
- 技术栈: [列出]
- 性能要求: [具体指标]
- 时间限制: [如有]

## 请输出
1. 架构图 (Mermaid 格式)
2. 核心组件说明
3. 数据流设计
4. 关键决策点及理由
5. 潜在风险及缓解方案
```

### 模板 3: Bug 修复

```markdown
## 问题描述
[现象描述]

## 期望行为
[应该是什么样]

## 实际行为
[实际是什么样]

## 重现步骤
1. [步骤]
2. [步骤]

## 相关代码
[代码片段]

## 已尝试
[你已经尝试过的方法]

## 环境
- Python 版本:
- 相关依赖版本:
- 操作系统:

请分析问题原因并提供修复方案。
```

## 常见陷阱与解决方案

| 陷阱 | 问题 | 解决方案 |
|------|------|----------|
| **模糊指令** | "帮我优化代码" | 明确优化目标: "将时间复杂度从 O(n²) 优化到 O(n log n)" |
| **缺少示例** | 输出格式不符合预期 | 提供 Few-Shot 示例 |
| **上下文不足** | LLM 猜测你的意图 | 提供项目背景、现有代码、约束条件 |
| **过度约束** | LLM 输出受限 | 只约束必要部分，给 LLM 空间发挥 |
| **一次问太多** | 输出质量下降 | 分步骤提问，每步聚焦一个子问题 |

---

## 效率提升对比

| 场景 | 朴素 Prompt | 结构化 Prompt | 提升 |
|------|-------------|---------------|------|
| 代码生成 | 反复修改 5-10 次 | 1-2 次即通过 | 3-5x |
| Bug 修复 | 描述不清导致误修 | 精准定位修复 | 2-3x |
| 架构设计 | 输出不符合需求 | 一次输出可用方案 | 2x |
| 代码审查 | 遗漏关键问题 | 全面覆盖审查维度 | 1.5x |

## Prompt 工程的进阶技巧

### 1. 迭代优化法

不要期望一次就得到完美结果，而是通过迭代来优化。

**步骤**：
1. 写出初始 Prompt
2. 评估 AI 输出
3. 识别问题（模糊、缺失、错误）
4. 优化 Prompt
5. 重复直到满意

**示例**：
- 第 1 轮："写一个排序函数" → 输出太泛
- 第 2 轮："用 Python 写一个快速排序函数" → 缺少细节
- 第 3 轮："用 Python 写一个快速排序函数，处理空列表和重复元素" → 接近完美

### 2. 分解复杂任务

将大任务分解为小步骤，每步聚焦一个子任务。

**反例**：
```
构建一个完整的电商后端，包括用户系统、商品管理、订单处理、支付集成。
```

**正例**：
```
步骤 1：设计用户系统的数据模型
步骤 2：实现用户注册和登录 API
步骤 3：添加 JWT 认证中间件
...（每步独立完成）
```

### 3. 使用元提示 (Meta-Prompting)

让 AI 帮你优化 Prompt。

**示例**：
```
我需要写一个 Prompt 来让 AI 生成高质量的 API 文档。
请帮我优化这个 Prompt，使其更清晰、更结构化。

我的初始 Prompt：
"帮我写 API 文档"
```

### 4. 条件约束

明确告诉 AI 什么能做，什么不能做。

**示例**：
```
请实现一个用户注册函数。

要求：
- 使用 Python 3.11+
- 必须有类型注解
- 必须有错误处理
- 不使用任何第三方库
- 代码行数 < 50 行
```

## Prompt 工程的心智模型

### 1. 清晰度 > 简洁度

宁可写长一点的 Prompt，也不要让 AI 猜测你的意图。

### 2. 示例 > 描述

给 AI 一个示例，比描述十次更有效。

### 3. 约束 > 自由

适当的约束能提高输出质量，而不是限制创造力。

### 4. 迭代 > 一次到位

好的 Prompt 是迭代出来的，不是一次写出来的。

---

## 总结

Prompt 工程是一项需要持续练习的技能。核心要点：

1. **明确性**：清晰表达你的需求
2. **结构化**：用 Markdown 组织 Prompt
3. **上下文**：提供足够的背景信息
4. **迭代**：通过反馈不断优化
5. **实践**：在真实项目中应用

记住：**好的 Prompt 不是让 AI 替你思考，而是让 AI 更好地辅助你思考。**

### 真实案例：Prompt 工程的力量

**Coinbase (2026)**：
- 2,400+ 开发者从"写代码"转向"定义意图"
- 从想法到生产时间从 20 天降至 1.8 天（90% 减少）
- 关键转变：工程师不再写代码，而是定义意图并验证结果

**关键洞察**：
- **意图定义 > 代码编写**：好的 Prompt 本质是清晰的意图表达
- **结构化输出**：JSON/YAML 格式的输出更容易被程序处理
- **迭代优化**：通过反馈循环不断优化 Prompt 质量

**Prompt 质量与开发效率的关系**：

| Prompt 质量 | 开发效率 | 代码质量 | 调试时间 |
|-------------|----------|----------|----------|
| 低（模糊） | 1x | 低 | 高 |
| 中（基本） | 2-3x | 中 | 中 |
| 高（结构化） | 5-10x | 高 | 低 |
