# 代码评审最佳实践

## 核心原则

代码评审不是找 bug，而是提升代码质量和知识共享。

### 评审目标

```
发现潜在问题 → 分享知识 → 统一标准 → 提升质量
```

## 评审流程

### 1. 评审前准备

**作者:**
- 确保代码通过所有测试
- 写清楚 PR 描述
- 标记需要重点关注的部分

**评审者:**
- 了解需求背景
- 阅读相关文档
- 预留足够时间

### 2. 评审重点

| 维度 | 检查要点 |
|------|----------|
| **正确性** | 逻辑是否正确，边界情况处理 |
| **可读性** | 命名是否清晰，结构是否合理 |
| **可维护性** | 是否易于修改和扩展 |
| **性能** | 是否有明显性能问题 |
| **安全性** | 是否有安全隐患 |

### 3. 评审反馈

**正面反馈:**
```
✅ 这个设计很优雅
✅ 处理了边界情况
✅ 测试覆盖全面
```

**改进建议:**
```
💡 考虑使用 X 替代 Y，因为...
❓ 这里为什么这样处理?
⚠️ 这里可能有并发问题
```

## 评审清单

### 功能性
- [ ] 代码是否实现了需求
- [ ] 边界情况是否处理
- [ ] 错误处理是否完善

### 代码质量
- [ ] 命名是否清晰
- [ ] 函数是否过长
- [ ] 重复代码是否提取

### 测试
- [ ] 单元测试是否覆盖
- [ ] 测试用例是否充分
- [ ] 测试是否可读

### 安全性
- [ ] 输入是否验证
- [ ] 敏感数据是否保护
- [ ] 权限是否检查

## 常见问题

| 问题 | 建议 |
|------|------|
| **评审太慢** | 设置 SLA，如 24 小时内完成 |
| **评审太粗** | 使用清单，逐项检查 |
| **冲突过多** | 建立编码规范 |
| **知识垄断** | 轮换评审者 |

## AI 辅助评审

```markdown
请帮我评审这段代码:

1. 检查代码质量
2. 发现潜在问题
3. 提出改进建议
4. 评估安全性
```

## 案例: 代码评审改进

### 改进前
- 评审时间: 3 天
- 发现问题: 5 个/PR
- 修复率: 60%

### 改进后
- 评审时间: 1 天
- 发现问题: 3 个/PR
- 修复率: 90%

### 改进措施
1. 建立评审清单
2. 设置评审 SLA
3. 使用 AI 辅助
4. 定期培训
