# 技术债务管理

## 核心原则

技术债务不是问题，不受控的技术债务才是问题。

### 技术债务分类

```
有意债务: 为了速度故意欠下的债务
无意债务: 由于知识不足造成的债务
```

## 识别技术债务

### 代码层面

| 信号 | 说明 |
|------|------|
| 重复代码 | 相同逻辑出现多次 |
| 过长函数 | 函数超过 50 行 |
| 复杂条件 | 嵌套超过 3 层 |
| 缺少测试 | 覆盖率低于 70% |

### 架构层面

| 信号 | 说明 |
|------|------|
| 紧耦合 | 模块间依赖过多 |
| 循环依赖 | A→B→C→A |
| 过度设计 | 简单问题复杂化 |
| 技术过时 | 使用过时的技术栈 |

## 评估债务

### 债务矩阵

```
         高影响
            │
    ┌───────┼───────┐
    │ 优先级高 │ 优先级中 │
    │  快速修复 │  计划修复 │
────┼───────┼───────┼────
    │ 优先级中 │ 优先级低 │
    │  计划修复 │  暂时忽略 │
    └───────┼───────┘
            │
         低影响
         高成本 ←──→ 低成本
```

### 量化指标

| 指标 | 计算方式 |
|------|----------|
| 债务比率 | 债务时间 / 总开发时间 |
| 修复成本 | 预估工时 × 人力成本 |
| 影响范围 | 受影响的模块数量 |

## 管理策略

### 1. 债务预算

**原则:** 每个 Sprint 预留 20% 时间处理债务

**分配:**
- 40% 紧急修复
- 30% 计划重构
- 20% 代码优化
- 10% 文档完善

### 2. 渐进式重构

**策略:**
```
小步修改 → 保持功能 → 持续测试 → 逐步改善
```

**实践:**
- 每次提交只改一个小问题
- 确保所有测试通过
- 不改变外部行为

### 3. 债务看板

```markdown
## 技术债务看板

### 紧急 (本周)
- [ ] 修复安全漏洞
- [ ] 解决性能瓶颈

### 计划 (本月)
- [ ] 重构认证模块
- [ ] 提升测试覆盖

### 跟踪 (持续)
- [ ] 代码重复
- [ ] 文档缺失
```

## 案例: 技术债务清理

### 背景
- 代码重复率: 15%
- 测试覆盖率: 45%
- 构建时间: 10 分钟

### 清理计划
- 第 1 月: 提升测试覆盖到 70%
- 第 2 月: 降低重复率到 5%
- 第 3 月: 优化构建到 3 分钟

### 结果
- 代码质量: A 级
- 开发效率: 提升 30%
- 缺陷率: 降低 50%
