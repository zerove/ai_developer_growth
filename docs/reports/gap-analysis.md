# 差距分析：规则引擎 vs 人类开发经验

> 当前项目有 780+ 条规则，覆盖 22 个类别，但人类几十年的开发经验远不止"检查代码模式"。

---

## 核心矛盾

| | 当前项目 | 人类经验 |
|--|---------|---------|
| **颗粒度** | 单文件、单模式 | 全系统、架构级 |
| **上下文** | 不知道文件角色 | 知道这是测试/核心/遗留代码 |
| **动态性** | 规则固定不变 | 经验持续积累和修正 |
| **判断** | 二元（对/错） | 权衡（值不值得修） |

---

## 7 个关键差距

### 差距 1：没有上下文感知（🔴 最大差距）

当前所有规则对所有文件一视同仁。`password = "xxx"` 在以下场景中的含义完全不同：

| 场景 | 应该怎么处理 |
|------|-------------|
| 测试文件中的测试凭据 | 应该允许（或只 warning） |
| 生产代码中的硬编码密钥 | 必须 error 阻止 |
| 遗留代码（有 `@deprecated` 标记） | 可以 warning 但不阻止 |
| 配置文件模板 | 应该跳过 |
| 快速原型/实验代码 | 降低严重度 |

**人类经验**：知道这个文件是测试还是生产、是新代码还是遗留代码、是核心逻辑还是配置。

**当前能力**：只有按文件名排除（`exclude_files`），需要手动维护。

### 差距 2：不能判断"值不值得修"（🔴 根本性问题）

代码质量不是越高越好。过度工程化是真实的成本：

- 一个只会在内部运行一次的脚本，不需要 90% 覆盖率
- 一个 20 行的工具函数，不需要拆分成 5 个文件
- 一个下个 sprint 就要重写的模块，不值得现在优化

**人类经验**：知道什么时候该严格、什么时候该放过。这是资深开发者和初级开发者的核心区别。

**当前能力**：没有区分能力。所有规则同等严格。

### 差距 3：没有"为什么不"的能力（🟡 可补）

规则告诉你 `except: pass` 有问题，但不解释：

- 为什么吞异常是危险的？（数据丢失、调试困难、安全漏洞）
- 什么场景下可以接受？（日志并退出、中间件层）
- 更好的替代方案怎么选？（具体看你想要什么行为）

**人类经验**：Reviewer 不仅指问题，还教思路。

**当前能力**：`fix_hint` 只有一句话。没有分层的学习引导。

### 差距 4：不从错误中学习（🟡 可补）

如果一个规则持续产生误报，人类 review 会：

- 发现误报
- 调整判断标准
- 下次不再犯同样错误

**当前能力**：
- `.adg/rules.yml` 允许手动禁用规则
- 但引擎不会自动分析误报模式
- `pattern_learner.py` 已实现但只做#统计#不做#学习#

### 差距 5：没有架构和设计层面的洞察（🔴 长远）

代码质量不仅仅是单文件内的模式：

| 架构维度 | 人类审查 | 当前能力 |
|---------|---------|---------|
| 模块耦合 | 能看出不该依赖的模块 | ❌ |
| 分层违规 | Controller 直接操作数据库 | ❌ |
| 过度抽象 | 为了"可扩展"加了4层接口 | ❌ |
| 抽象不足 | 业务逻辑散落在各处 | ❌ |
| 循环依赖 | 知道模块间不该相互引用 | ⚠️ `ImportGraph.find_cycles` 已实现 |

### 差距 6：领域知识的缺失（🔴 长远）

最好的代码规范来自领域本身：

| 领域 | 特殊要求 |
|------|---------|
| 金融 | 事务一致性、审计日志、金额精度 |
| 医疗 | HIPAA、数据加密、访问审计 |
| 游戏 | 帧率敏感、内存预算、编译时间 |
| 嵌入式 | 内存有限、实时性、硬件交互 |

**当前能力**：没有领域感知。

### 差距 7：没有团队自适应能力（🟡 可补）

100 个团队有 100 套代码规范。有的强制类型注解，有的禁止 Optional，有的要求所有函数必须有文档。

**当前能力**：`.adg/rules.yml` 支持自定义，但从零开始配置成本高。没有"学习团队代码库"的能力。

## 真正可行的补足方向

### 短期（当前架构内可做）

| 方向 | 投入 | 收益 |
|------|------|------|
| **上下文标记系统** — 在文件头或目录结构中标记文件角色（test/prod/legacy/prototype），规则根据不同角色调整严重度 | 2-3h | 大幅降低误报率 |
| **规则权重体系** — 同一规则在不同上下文中权重不同，通过 `.adg/config.yml` 配置 | 1h | 团队可调优 |
| **`fix_hint` 升级** — 从一句话扩展为"问题→原因→方案→示例"四段式 | 0.5h | 教学效果提升 |
| **误报回馈机制** — 用户标记误报后，规则引擎记录并降低该规则的优先级 | 2h | 持续改善 |

### 中期（需新功能开发）

| 方向 | 说明 |
|------|------|
| **架构规则引擎** — 跨文件分析、模块依赖、分层违规检测 | 需要 AST + 依赖图 |
| **团队规范学习** — 分析团队现有代码库，自动生成 `.adg/rules.yml` | 基于 `pattern_learner` 扩展 |
| **领域规则包** — 金融/医疗/游戏等领域的预设规则集合 | 内容工作，非代码 |

### 长期（需 AI 能力突破）

| 方向 | 说明 |
|------|------|
| **AI 辅助判断** — LLM 参与"值不值得修"的权衡判断 | 依赖 jcode 平台能力 |
| **设计评审自动化** — 对架构变更进行影响分析 | 需要跨文件理解能力 |

---

## 我的看法

当前项目在**代码层面的模式检测**已经做到很不错了（780 条规则、22 个类别、26 种语言）。但人类经验的核心价值不在"发现错误"而在"判断优先级"和"教人思考"。

**最有价值的下一步**不是加更多规则，而是**给规则装上"上下文眼睛"** —— 让规则知道自己在看什么文件、什么项目、什么阶段。这个方向只需要 2-3 小时，就能让 780 条规则的误报率大幅下降。
