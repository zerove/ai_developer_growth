    微服务架构¶

    核心原则¶

    微服务 = 单一职责 + 独立部署 + 轻量通信

    架构设计¶

    1. 服务划分¶

    原则: - 业务边界清晰 - 数据独立 - 可独立部署

    划分方法: 

    领域驱动设计 (DDD)
├── 识别领域
├── 划分子域
├── 定义限界上下文
└── 设计服务边界

    2. 服务通信¶

    同步通信: 

    REST API
├── 优点: 简单、易调试
├── 缺点: 耦合度高
└── 适用: 简单查询

gRPC
├── 优点: 高性能、强类型
├── 缺点: 调试复杂
└── 适用: 内部通信

    异步通信: 

    消息队列
├── 优点: 解耦、异步
├── 缺点: 复杂度高
└── 适用: 事件驱动

事件总线
├── 优点: 松耦合、可扩展
├── 缺点: 一致性难保证
└── 适用: 最终一致性

    3. 数据管理¶

    数据库策略: 

    每服务一数据库
├── 优点: 数据隔离
├── 缺点: 跨服务查询复杂
└── 适用: 强隔离需求

共享数据库
├── 优点: 查询简单
├── 缺点: 耦合度高
└── 适用: 强一致性需求

    常见模式¶

    1. API 网关¶

    功能: - 路由转发 - 认证授权 - 限流熔断 - 日志监控

    实现: 

    # Kong 网关配置
routes:
  - name: user-service
    paths: ["/api/users"]
    service: user-service
    plugins:
      - name: rate-limiting
        config:
          minute: 100

    2. 服务发现¶

    客户端发现: 

    服务注册 → 客户端查询 → 负载均衡 → 调用服务

    服务端发现: 

    服务注册 → 负载均衡器 → 路由到服务

    3. 熔断器¶

    状态: 

    关闭 → 打开 → 半开 → 关闭

    配置: 

    # Python 断路器
from pybreaker import CircuitBreaker

breaker = CircuitBreaker(fail_max=5, reset_timeout=60)

@breaker
def call_service():
    return requests.get("http://service/api")

    监控和运维¶

    1. 分布式追踪¶

    Jaeger 架构: 

    服务 → Agent → Collector → Query → UI

    2. 日志聚合¶

    ELK Stack: 

    Logstash → Elasticsearch → Kibana

    3. 指标监控¶

    Prometheus + Grafana: 

    服务 → Prometheus → Grafana → 告警

    最佳实践¶

    1. 容错设计¶

    策略: - 超时控制 - 重试机制 - 降级处理 - 熔断保护

    2. 数据一致性¶

    最终一致性: 

    事件发布 → 消费处理 → 状态更新

    Saga 模式: 

    正向操作 → 失败 → 补偿操作

    3. 安全设计¶

    认证授权: - OAuth 2.0 - JWT Token - 服务间认证

    常见问题¶

    问题 原因 解决方案
    服务雪崩 级联故障 熔断降级
    数据不一致 分布式事务 最终一致性
    部署复杂 服务多 自动化部署

    案例: 微服务改造¶

    背景¶

    • 单体应用
    • 部署复杂
    • 扩展困难

    改造方案¶

    1. 拆分为 5 个微服务
    2. 使用 gRPC 通信
    3. Kubernetes 部署

    结果¶

    • 部署时间: 1 小时 → 5 分钟
    • 扩展能力: 手动 → 自动
    • 故障恢复: 小时级 → 分钟级
